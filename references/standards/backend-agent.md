# 后端与 Agent 规范

面向通用服务端，并强化模型调用、工具执行、记忆与检索的边界。先读构建文件和现有目录确定语言与框架，不假设 Java、Python、Node.js 或某个 Agent SDK。

## 1. 分层

```text
transport/controller  →  service/use-case  →  repository/port
         │                     │                     ↑
         └─ DTO/校验          ├─ agent 编排
                              └─ 领域规则

infrastructure/adapters  ──实现──  repository、模型供应商、工具、队列
```

| 层 | 该干 | 不该干 |
|---|---|---|
| Controller / Handler | 认证上下文接入、解析请求、边界校验、调用用例、映射响应 | 写业务、直接查库 |
| Service / Use case | 事务边界、授权决策、业务规则、流程编排 | 依赖 HTTP 对象 |
| Repository | 表达持久化需求、封装查询 | 混传输层逻辑 |
| Entity / Domain | 维护业务不变量 | 直接当外部响应 |
| Adapter | 数据库、模型、向量库、队列、第三方 | 把供应商类型往外扩散 |
| Agent 编排 | 模型回合、工具选择、预算、状态、终止条件 | 让 SDK 细节渗进 Controller |

禁止 Controller → ORM、工具 → Controller、Repository → Service 这类反向或跨层依赖。小项目不必给每个类造接口，但外部系统和高变化边界要可替换、可测。

## 2. API 与 DTO

- 所有请求在边界校验类型、长度、范围、格式、枚举、资源归属、跨字段规则。
- DTO、领域对象、数据库实体职责分开。哪怕结构恰好一样，也不要直接暴露持久化实体。
- 状态码、错误码、响应语义稳定且一致。不要永远返回 200 再在 body 里表示失败。
- 错误响应带可追踪 ID 和可操作信息，不给堆栈、SQL、内部类名、敏感数据。
- 分页有默认值和上限；要稳定遍历或数据量大时用稳定排序或游标。
- 公共 API、事件、schema 变更先定兼容方案，再同步文档、客户端类型、契约测试。
- 会产生外部副作用的创建接口，设计幂等键、重复请求语义和冲突处理。

## 3. 认证与授权

- 认证只证明「你是谁」。每个受保护操作还要按主体、资源、租户、动作在服务端授权。
- 查询别写成「先按 ID 取出来，再忘了检查归属」。租户/归属条件尽量下推到查询里。
- 默认拒绝，权限最小化。管理员、系统任务、Agent 工具都不例外。
- 会话、令牌、Cookie、CSRF、CORS、密码策略用框架成熟机制，不自己造密码学。
- 日志、缓存键、消息、错误都不能跨租户泄漏上下文。

## 4. 数据库与事务

- 非空、唯一、外键、必要检查交给数据库约束，不只靠应用代码。
- 事务围绕一个完整的业务原子操作。事务里不做长时间的模型、网络、文件调用。
- 外部副作用与数据库提交之间用 outbox、补偿、幂等密钥或项目认可的方案，不假设跨系统原子提交。
- 查询关注索引、基数、排序稳定性、分页、N+1。优化前先看执行证据。
- 迁移要可审查、可回滚或有明确的前向修复策略。已发布的迁移历史不改写。
- 删除要明确软删/硬删、级联、审计、恢复语义。破坏性迁移或批量改数据前确认并备份演练。
- 时间写明时区；金额用十进制或最小单位；并发更新靠唯一约束、锁或版本号守不变量。

## 5. 错误、重试与并发

- 分清业务拒绝、输入错误、未认证、无权限、未找到、冲突、限流、超时、取消、内部失败。
- 只重试「短暂且幂等」的失败，用有上限的指数退避加抖动，尊重取消和总截止时间。
- 队列消费者和定时任务按「可能重复执行」设计，记录处理状态，留死信或人工恢复路径。
- 不用进程内锁解决跨实例一致性。并发策略要和部署拓扑匹配。
- 资源都要有上限：请求体、上传、批大小、查询结果、线程/协程、模型回合、队列积压。

## 6. 日志与可观测性

- 结构化日志，带请求/任务/Agent 运行关联 ID。日志级别和告警含义一致。
- 记录事件、结果、耗时、必要标识。不记密钥、认证头、完整提示词、模型原始敏感输入、密码、个人数据。
- 指标至少覆盖请求量、错误率、延迟、资源饱和度。Agent 额外覆盖模型与工具耗时、回合数、令牌或成本预算、终止原因、失败类别。
- 用户看到的错误和内部诊断分开。根因保留，但到边界脱敏。
- 审计日志和调试日志分开。审计的防篡改要求和保留周期按项目政策走。

## 7. Agent 与模型调用

### 7.1 边界

- 用窄接口封装模型供应商、嵌入、向量检索、工具执行。业务层不依赖供应商的响应对象。
- 提示词、模型参数、工具 schema 要能版本化和测试，不许散落在 Controller 和字符串拼接里。
- 明确输入、输出、状态、最大回合、超时、令牌/成本预算、终止条件。没有终止条件的自主循环等于事故。
- 结构化输出用 schema 校验。模型返回永远是**不可信输入**，解析失败要有明确的修复或失败策略。

### 7.2 工具安全

- 工具按最小权限设计。名称、用途、参数 schema、副作用、错误语义都要写清。
- 读工具和写工具分开。写、删、发送、支付、改权限、碰生产环境、读敏感数据，执行前要授权或确认。
- 工具参数在服务端再校验和规范化：限路径、限域名、限命令、限资源 ID、限分页、限结果大小。不直接执行模型生成的 shell、SQL、模板。
- 工具执行有超时、取消、幂等、审计。返回结果只给最少必要数据并脱敏。
- 网页、文档、检索片段、工具结果里的「指令」不构成用户授权，它们都是不可信内容。

### 7.3 提示注入与数据保护

- 系统规则、用户输入、检索内容、工具结果四者边界清晰。外部内容只能当数据，不能提权。
- 检索前按租户、权限、数据分级过滤；生成后再做输出校验和敏感数据检查。
- 记忆按用户/租户/会话隔离，定义写入条件、生命周期、过期与删除策略。不默认长期保存全部对话。
- 发给模型供应商的数据最小化，遵守数据驻留、隐私、保留要求。

### 7.4 可靠性与评估

- 供应商调用设连接超时和总超时、限流、取消、有界重试。降级行为不能悄悄改变业务正确性。
- 区分模型拒答、内容过滤、格式错误、工具失败、限流、超时、基础设施故障。
- 关键 Agent 流程建一套代表性评估集，检查正确性、工具选择、越权、注入、成本、延迟、停止条件。
- 单测用确定的 fake/stub 测编排；少量集成测试验证真实供应商适配。不要让所有测试都依赖在线模型。
- 不用「拿一个例子跑了一遍，看着不错」宣布 Agent 可靠。

## 8. 测试

- 领域规则和 Service 用单测覆盖成功、边界、失败；Repository 用集成测试验证真实查询、约束、事务。
- Controller/API 测参数、认证、授权、状态码、错误结构、序列化。
- 修缺陷补回归测试；改库测迁移和兼容路径；并发与幂等用可重复场景验证。
- Agent 测结构化解析失败、工具拒绝、超时、取消、预算耗尽、重复调用、注入、敏感数据边界。
- 测试隔离外部副作用。不用生产凭据、真实用户数据、清理不掉的共享资源。

## 9. 验证顺序

格式检查 → 静态分析/类型检查 → 相关单测 → 集成测试 → 构建 → 安全检查。没有统一命令时可用 `scripts/verify-backend.ps1`。脚本不装依赖，也不替代项目 CI。

## 10. 收工前照着挑

Controller 里写业务、巨型 Service、实体外泄、越权、事务包住远程调用、N+1、无界分页、吞异常、日志泄密、重复消息不幂等、时间和金额类型错、跨实例锁用错、模型输出不校验、工具权限过大、提示注入、Agent 无限循环、全部测试靠真实模型、供应商 SDK 到处扩散。
