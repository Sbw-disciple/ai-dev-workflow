# 规矩

一个人用，不需要面面俱到。下面每条都是能直接照做的，不是价值观。

## 1. 动手前先读

- 读构建文件、目录结构、`git log -3`、有没有测试
- 只写从文件里确认的事实，不靠目录名猜行为
- 技术栈判断不出来、且不同选择会明显改变结果时，才去问

## 2. 改代码

- 最小完整改动。不顺手清理、不全文件格式化、不顺手删「看着没用」的代码
- 拆文件看职责边界，不看行数
- 生成物、锁文件、数据库迁移用工具改，不手编
- 新依赖先问（红线 2）

## 3. Python 脚本（你最常写的）

- 标准库优先，要第三方先问
- 路径用 `pathlib`，不用字符串拼
- 读写文件显式 `encoding="utf-8"`；Windows 下注意 `\r\n`，需要一致就 `newline=""`
- CLI 用 `argparse`；`--check` 这类只读模式不许改文件
- 退出码要有意义：`0` 成功、`1` 失败、`2` 只是警告
- 报错说清「哪一步 / 哪个文件 / 怎么改」

## 4. Markdown 与文档仓库（写 skill、写作业）

- 一个文件只讲一件事；超过 200 行就拆
- 标题层级不要跳：`#` → `##` → `###`
- 表格用来对比，清单用来执行，不要混着用
- 改了行为，同步改 README 和 CHANGELOG

## 5. 提交与发版

- 提交信息一行说清做了什么，别写 `update`、`fix bug`
- 一次提交一件事，不把无关改动混进来
- 发版三处同步：`SKILL.md` 的 `version`、`CHANGELOG.md`、`README.md`（如果有提版本）
- 打标签：`git tag -a v0.5.0 -m "说明"`，和提交一起推

## 6. Windows 上踩过的坑

| 坑 | 现象 | 处理 |
|---|---|---|
| `.ps1` 含中文 | PS 5.1 下乱码、解析报一串错 | 文件存 UTF-8 **带 BOM** |
| npm 脚本用了 unix 命令 | `find: missing argument to '-exec'` | `npm config set script-shell "C:/Program Files/Git/bin/bash.exe"` |
| 一轮里删太多文件 | `SAFE_DELETE_BULK_CONFIRM_REQUIRED` | 单轮删 >50 个会被拦，分批做或先问 |
| Git Bash 与 Windows 路径 | `/d/...` 与 `D:\...` 混用报错 | 命令行用 `/d/`，传给 Python 用 `D:/` |

## 7. 要你决定时怎么问

一次说全四件：**事实 / 不处理会怎样 / 两个选项 / 推荐哪个**。不挤牙膏，不问「你觉得呢」。

## 8. 报告里不写的东西

令牌、密码、个人数据、完整环境变量、敏感业务内容。路径可以写。
