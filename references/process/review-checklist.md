# 两路评审清单

评审输出到 `.ai/review.md`。分两路，**不要混在一起看**——先看规范，再看规格，两件事互相干扰。

---

## A 路 · 仓库规范

不看功能对不对，只看这段代码像不像这个仓库里本来就有的代码。

### 命名与结构

- [ ] 新增文件放在现有分层对应的目录里，没有另起一套结构
- [ ] 文件名、类名、函数名、变量名的风格与邻近文件一致
- [ ] 没有引入新的目录约定（除非规格里明确要求）

### 依赖

- [ ] 没有引入规格之外的新依赖
- [ ] 没有为了一个小功能引入一个大库
- [ ] 没有重复实现仓库里已有的工具函数

### 错误处理与边界

- [ ] 失败路径有处理，不是只写了 happy path
- [ ] 空值、越界、超时、并发有考虑
- [ ] 错误信息对用户可读，不是异常堆栈直接抛给界面

### 可维护性

- [ ] 没有复制粘贴的大段重复逻辑
- [ ] 注释解释「为什么」，不复述「做了什么」
- [ ] 没有留下调试代码、临时打印、写死的测试数据
- [ ] 没有注释掉的大段旧代码（该删就删，版本控制会记得）

### 一致性

- [ ] 日志、埋点的写法与其他模块一致
- [ ] 配置项没有硬编码在业务代码里

---

## B 路 · 规格一致性

对照 `.ai/CONTEXT.md` 逐条过，每一条都要给出结论。

### 范围

- [ ] 规格里「做什么」的每一条都有对应实现
- [ ] 规格里「不做什么」的每一条都没有被顺手做掉
- [ ] 没有新增规格之外的功能（哪怕看起来很有用）

### 验收标准

逐条填表：

| 编号 | 标准 | 实现位置 | 是否满足 | 证据 |
| --- | --- | --- | --- | --- |
| AC-1 |   |   | 是 / 否 / 部分 |   |

### 约束

- [ ] 没有动「不可动」清单里的模块
- [ ] 没有修改既有数据结构（若修改，规格里有说明）
- [ ] 新代码遵守命名与目录约定

### 偏差处理

发现偏差时，只有两种正确做法：

1. **改代码**，让它回到规格
2. **改规格**，说明为什么原规格不合理，同步更新 `CONTEXT.md` 并记录变更

不允许第三种：让代码和规格各说各话。

## 评审结论

```markdown
## 结论：有条件通过

### 必须修复
1. `RecordPage.ets:88` 在数据为空时直接 return，未渲染空状态，违反 AC-2
2. 新增依赖 `dayjs` 未在规格中列出，且项目已有 `formatDate` 工具

### 建议（不阻塞）
1. 列表项渲染可抽成子组件，当前单文件 400 行偏长

### 规格偏差
无
```

三种结论：

| 结论 | 含义 |
| --- | --- |
| 通过 | 两路都无阻塞项，可以进入回归 |
| 有条件通过 | 列出必须修复项，修完自查即可，不必重走评审 |
| 打回 | 存在方向性偏差，回到阶段 5 重做对应 ticket |

---

## 一个提醒

评审时最容易犯的错，是**顺手把问题改了**。评审和执行必须分开：审查者只出结论，修改由实现方按结论做。混在一起，就没人对「改得对不对」负责了。
