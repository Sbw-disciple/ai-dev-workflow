# 七阶段细则

`SKILL.md` 只给速查表，这里放每个阶段的具体规则。按档位跳着读，不用全看。

档位对照：L0 全部跳过；L1 只看阶段 1（判据）、5、7；L2 走 1、3（精简）、5、7；L3 走满 0 到 7。

---

## 阶段 0 · 读项目

**静默执行，不拿能被读出来的事问用户。**

读构建文件（`package.json` / `build-profile.json5` / `pyproject.toml` / `pom.xml`）、目录结构、`git log --oneline -3`、分支状态、已有测试方式、`AGENTS.md` 等项目规则。

输出一句话：`这是一个 <技术栈> 项目，主要模块 <A/B/C>，当前 <干净/有未提交改动>。`

目录为空或没有代码，跳到阶段 1。

---

## 阶段 1 · 澄清

**规则**

- 一次只问一个问题，等回答再问下一个，最多 5 个
- 每个问题**先给建议答案**，用户说「对」或纠正即可，降低回答成本
- 用户说「你定」时按建议定，记进规格的「假设」一节

**问题优先级**

1. 谁在什么情况下用它
2. 明确**不做**什么（最能防跑偏，必问）
3. 涉及哪些模块或文件，有没有不能动的地方
4. 怎么算做完，说一个能观察到的结果
5. 有没有性能、兼容、数据格式的约束

**出口**：一段不超过 8 行的需求复述，用户确认。

L1 只做第 2 问和第 4 问，各一句。

---

## 阶段 2 · 方案与对抗审查

**写方案**，到文件级：改哪些文件、各自为什么；数据从哪来到哪去；最可能出错的两三处；改坏了怎么退（一行能跑的命令）。

**对抗审查，不许跳过。** 有子代理就派一个，指令固定：「只找问题，不给方案。列出这个设计最可能失败的三个地方，以及两个没有交代清楚的前提。」没有子代理就在回复里单起一段红队视角，逐条挑战自己的假设：这个前提不成立会怎样？边界输入是什么？失败时用户看到什么？

**合并**：问题逐条处理，标 `已消解`（说明怎么改）或 `接受风险`（说明为什么能接受）。未处理完不进下一阶段。

**Gate 1**：给用户不超过 15 行的方案摘要，问「按这个做？」。同时逐条回答八条红线是否触碰。

---

## 阶段 3 · 写规格

用 `references/process/spec-template.md` 生成 `.ai/CONTEXT.md`。没有 `.ai/` 就先跑：

```bash
python <SKILL_DIR>/scripts/init_workspace.py <项目目录>
```

必含五节：

| 节 | 要求 |
|---|---|
| 目标 | 一句话，不用术语 |
| 范围内 / 范围外 | 范围外要具体，写「不做登录」而不是「其他不做」 |
| 验收标准 | 每条可判定，写不出「怎么证明」的删掉 |
| 约束 | 技术栈、目录、命名、不可动模块、性能底线 |
| 子任务与依赖 | 编号 + 依赖关系 |

写法对照：

- 不合格：`用户可以查看历史记录`
- 合格：`进入记录页按日期倒序显示最近 30 条；无记录时显示空状态；下拉可刷新`

L2 用精简版（目标 + 范围 + 3 到 5 条验收），
L3 用完整版并带子任务表。

**Gate 2**：让用户重点确认「范围外」和「验收标准」两节。

---

## 阶段 4 · 拆 tickets

用 `references/process/tickets-template.md` 写 `.ai/tickets.md`。

- 3 到 7 张。超过 7 张说明这个需求该分期
- 每张必须写：编号、目标、涉及文件、验收判据、依赖、状态
- 粒度判据：**不了解背景的人十分钟能读懂这张的改动**
- 依赖成链的排前面，能并行的标 `可并行`

拆完自查：有没有哪张单独拿不出来验收，有就合并或重拆。

L1 不建文件，在回复里列一行「判据：xxx」即可。

---

## 阶段 5 · 逐张实现

每张按顺序：

1. **先写判据** —— 有测试框架就写测试并跑一次确认它是红的（不红说明没测到东西）；没有就写 3 到 5 条可观察判据，贴在该 ticket 下
2. **最小改动实现** —— 只动这张范围内的文件
3. **验证** —— 跑测试，或按判据逐条自查
4. **更新状态** —— `tickets.md` 里标 `done`，写一行实际改动

**禁止**：跨 ticket 顺手优化、改无关文件、加没被要求的功能。发现新问题记进 `tickets.md` 末尾的「待办」，不当场做。

实现时按技术栈加载 `references/standards/` 对应文件。有意义的改动追加一行到 `.ai/operations.md`。

---

## 阶段 6 · 两路评审

用 `references/process/review-checklist.md` + `references/checklists.md`，输出 `.ai/review.md`。

- **A 路 · 仓库规范** —— 命名、目录归属、依赖引入、错误处理、日志、注释密度是否与现有代码一致；对应技术栈的清单逐项过
- **B 路 · 规格一致性** —— 对照 `CONTEXT.md` 逐条查：有没有多做、少做、做偏

发现问题**先改设计再改代码**。直接打补丁会把规格和实现越拉越远。

结论只有三种：`通过` / `有条件通过（列条件）` / `打回（列问题）`。

---

## 阶段 7 · 回归

按 `CONTEXT.md` 的验收标准逐条验，出一张表：验收标准 / 结果 / 证据（截图、日志、测试名）。有一条没过就回阶段 5，不许「先提交再说」。

验证顺序：格式 → Lint / 静态分析 → 类型检查 → 单元测试 → 集成测试 → 构建 → 安全检查。只跑项目已有且已授权的命令；没有统一命令时用 `scripts/verify-frontend.ps1` / `verify-backend.ps1`。

最后写报告：L1 三行，L2 用简版（需求 / 改了什么 / 验证结果 / 没验证的 / 风险），L3 用 `references/report-template.md` 完整版。

**「未运行的检查」这一节必须填**，它是报告里最值钱的部分。

---

## 降级模式：没有测试框架

移动端、小程序、桌面端常常没有可跑的单测。不硬套 TDD，但要保住它想要的东西——可执行的验收判据。

| 部分 | 做法 |
|---|---|
| 纯逻辑（计算、换算、解析、状态机） | 抽成不依赖 UI 的函数，必须有测试或可运行的验证脚本 |
| UI 与交互 | 用验收判据代替：进入页面看到什么、点击后发生什么、异常输入如何提示、数值是否正确 |
| 回归范围 | 每次只回归受影响页面，控制手动成本 |

写不出判据的地方，通常就是需求没想清楚，退回阶段 1。

## 反模式

| 症状 | 后果 | 纠正 |
|---|---|---|
| 规格写成需求复述 | 无法判定完成，AI 自己定标准 | 每条验收标准都能回答「怎么证明」 |
| 同一个上下文既设计又审查 | 审查变成自我解释，问题一个挑不出 | 换子代理，或显式切红队视角 |
| 测试只要求「能跑通」 | 覆盖率上去了，错误被固化成预期行为 | 先跑红，再实现，跑绿 |
| 增量切得太大 | 审查看不懂，不敢回滚 | 一张 ticket 一次提交，diff 十分钟读完 |
| 档位定低了 | 看着轻量，实际改到半个仓库 | 中途发现超范围立刻升档，别硬装 |
| 全部 reference 一次读完 | 上下文被稀释，重点抓不住 | 按档位和技术栈只读需要的 |
